# Инвентарь

## Управление
- Tab — открыть/закрыть рюкзак; Esc — закрыть открытый инвентарь.
- E рядом с предметом/сундуком — подобрать/открыть.
- ЛКМ: перетащить весь стак между ячейками, в том числе между сундуком и рюкзаком.
- Одинаковые предметы объединяются до MaxStackSize; разные меняются местами.
- ПКМ в рюкзаке — использовать UsableItem. Зелье восстанавливает 25 HP и расходуется только при нехватке здоровья.
- Для выброса перетащить стак из рюкзака в нижнюю область.

В базовой сцене сундук рядом с точкой появления хоста (5.5, 0.4, -6.2), кристалл — около центра. В рюкзаке изначально три зелья. Тестовый слот экипировки не принимает предметы и не имеет механик.

## Ресурсы и компоненты
- Item: DisplayName, Description, Model (PackedScene с корнем Node3D), MaxStackSize, Weight, Rarity.
- Редкости: Common/обычный, Rare/редкий, Epic/эпический, Mythic/мифический, Legendary/легендарный. Цвет и энергия света определены в Item.
- Stack: Item, ItemCount. Ресурсы Item общие, стаки копируются для каждого экземпляра инвентаря/подбираемого объекта.
- UsableItem: переопределить Use(Player), вернуть true только при успешном применении. Эффект выполняется сервером.
- InventoryComponent можно добавить дочерним узлом любого объекта. MaxSlots и начальный массив Slots настраиваются до входа в дерево (инспектор). Не занятые ячейки — null.
- В сетевой игре изменять инвентарь через InventoryService; Add/Transfer — серверные примитивы, сами RPC не отправляют. После серверных изменений вне сервиса вызвать Publish().
- Новые типы сетевых контейнеров подключаются через проверку доступа InventoryService.Resolve; Chest уже подключён.
- Для новых предметов сохранять Item отдельным .tres: по сети передаётся ResourcePath, одинаковый на всех клиентах. Модели демонстрационных предметов центрированы около нуля, размер около 0.7 единицы; так же готовить другие UI-модели.
- Торговые товары задаются в `items/trade_items.json` полями `Id`, `ItemPath` и базовой `Price`. В `NPC.TradeItemIds` перечисляются ID товаров конкретного торговца. Сервер принимает предложения не ниже 30% базовой цены, проверяет баланс и свободный слот, затем списывает деньги и добавляет один предмет. Начальный баланс задаётся через `Player.StartingMoney`.
- Оружие наследуется от Equipment → Weapon → MeleeWeapon → Sword. Для оружия задаются `WeaponModel` и трансформ прикрепления. `EquipmentComponent` одновременно хранит один слот оружия и прикрепляет его модель к персонажу. Перетащите оружие между рюкзаком и секцией «Оружие»; сервер переносит сам предмет, поэтому перенос в рюкзак или выброс очищает слот и снимает модель с руки. Слот включён в обычные снимки инвентаря.
- `Weapon` задаёт `Damage`. `AnimatedEntity` использует `CombatStatsComponent` (сила 10, телосложение 2) и создаёт хитбокс Area3D на каждой кости скелета. В начале замаха импульс равен `Strength - Weapon.Weight`; каждое новое попадание по кости наносит урон оружия и уменьшает импульс на телосложение цели. При импульсе <= 0 хитбокс меча выключается; также он выключается по завершении анимации атаки.
- `RangedWeapon` задаёт скорость снаряда, требуемый `WeaponProjectile`, сцену снаряда и минимальное/максимальное время натяжения. Удержание ЛКМ натягивает тетиву, отпускание раньше минимума отменяет выстрел, а после максимума выстрел наносит полный урон. Между порогами урон растёт от 50% до 100% по доле натяжения. Сервер проверяет экипировку и наличие стрел, списывает одну стрелу и создаёт снаряд; попадание наносит урон только на сервере. Состояния натяжения, удержания и выстрела передаются остальным игрокам. Bow-клипы фильтруются по костям верхней части тела и смешиваются поверх locomotion, поэтому можно стрелять на ходу.
- `WeaponProjectile` — предмет-боеприпас с моделью. Его `Model` создаётся внутри `WeaponProjectileScene` при инициализации; ресурс получает направление, скорость и рассчитанный урон от экипированного `RangedWeapon`. Пример лука и стрелы: `items/bow.tres` и `items/arrow.tres`.
- PickUpObj.Slot назначается до AddChild: при _Ready создаются модель и свет из Item. Выброс делает это автоматически.
- Для подбора предмета врагом включите `PickUpObj.AIGatherable`: объект получит задачу Collect с требованием навыка Gathering. `EnemyGolem` имеет этот навык; собранный предмет попадает в его инвентарь через `InventoryService`.
- Чтобы враг лутал сундук, назначьте ему `Task` типа Loot. В `Task.RequiredRace` укажите расу владельца: враг лутает сундук другой расы; `None` разрешает лутать независимо от расы. Содержимое переносится в инвентарь врага через `InventoryService`, задача завершается, когда сундук опустеет.
- При смерти `AnimatedEnemy` сервер создаёт реплицируемый `DeadChestLoot` с копиями всех непустых стаков из рюкзака и экипировки; число слотов равно числу таких стаков. Он исчезает через минуту или после опустошения. Обычный сундук снова получает задачу `Required`, когда в него добавляют предметы. Для атаки мечом врагу также нужен навык `MeleeCombat`.

## Состояния и сеть
PlayerStateMachine имеет состояния Locomotion, Inventory, Chest, Trading, Disabled и вложенные состояния движения Idle/Walking/Crouching/CrouchWalking/Airborne, события переходов, вход/выход и блокировку камеры/атак/движения. Во время инвентаря гравитация продолжает работать. Сундук закрывается сервером при удалении/выходе из допустимой дистанции. Баланс хранится сервером и реплицируется вместе со снимком инвентаря.

InventoryService создаётся NetworkManager по одинаковому пути. Сервер проверяет отправителя RPC, дистанцию, доступ к контейнеру, индексы и ревизию. Устаревший перенос отклоняется: повторить drag после обновления. Все операции передают полные снимки инвентарей, pickup-объектов и открытых сундуков; это простой вариант для небольших сессий. Позднее подключение запрашивает актуальный снимок. Движение остаётся с существующей клиентской authority, как в исходной архитектуре.

MultiplayerSpawner единолично создаёт игроков на клиентах; authority назначается по имени узла до входа дочерних узлов в дерево.

## Проверки
```powershell
dotnet build --no-restore
& $godot --headless --path E:\YandexGame res://tests/inventory_tests.tscn
```
Для сетевого теста запустить два процесса (хост первым, клиент через 2 секунды):
```powershell
& $godot --headless --path E:\YandexGame res://tests/inventory_tests.tscn -- --network-host
& $godot --headless --path E:\YandexGame res://tests/inventory_tests.tscn -- --network-client
```
Тесты проверяют вместимость, overflow, перенос, закрытый сундук, устаревшие команды, лечение, выброс/подбор, состояния, реальную клиент-серверную репликацию и снимок при позднем подключении. Флаг --preview без --headless сохраняет изображение UI в %TEMP%/inventory-preview.png. Автоматические тесты вызывают те же серверные команды, что UI; ручные жесты мышью отдельно не автоматизированы.
